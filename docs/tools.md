# Native Wine developer tools

`wmc`, `wrc` and `widl` run directly on Linux x86_64/ARM64, macOS ARM64 and
Windows x86_64/ARM64. The pinned `wine-tools` archives come from the same
[11.20.2 release](https://github.com/hermeticbuild/wine-prebuilt/releases/tag/11.20.2)
as the runtime archives. Tools-only actions do not acquire or build a Wine
runtime, supervisor, FEX or consumer C/C++ compiler. Linux tools require glibc
2.17 or newer; the macOS tools declare a 26.5 deployment minimum.

## Register tools

Native tools are unreleased. Use the current checkout until a release includes
this API:

```starlark
bazel_dep(name = "rules_wine", version = "0.1.2")
local_path_override(module_name = "rules_wine", path = "../rules_wine")
wine = use_extension("@rules_wine//wine/extension:wine.bzl", "wine")
use_repo(wine, "wine_tools_toolchains")
register_toolchains("@wine_tools_toolchains//:all")
```

Published `rules_wine` 0.1.2 contains only the runtime APIs.

`wine_toolchains` and `wine_tools_toolchains` are independently imported and
registered. The extension has no tags. To register a subset, name an individual
tools registration such as `@wine_tools_toolchains//:linux_x86_64`.

## Message tables

```starlark
load("@rules_wine//wine:wine_message_file.bzl", "wine_message_file")

wine_message_file(
    name = "messages",
    src = "messages.mc",
    out = "messages.rc",
)
```

This emits `messages.rc` and the implicit output label `messages.h`. RC mode
accepts an optional `header = "custom_messages.h"` output name and uses `-i`:
each message table is inline, avoiding language-dependent `.bin`
outputs. For a binary resource directly, set `output_format = "res"` and
`out = "messages.res"`. This mode emits no header, matching upstream `wmc`.
Both modes request Unicode message tables (`-U`). Input defaults to the message
source's codepage; `unicode = True` means UTF-16 input (`wmc -u`), not UTF-8.

## Resources

```starlark
load("@rules_wine//wine:wine_resource_file.bzl", "wine_resource_file")

wine_resource_file(
    name = "resources",
    src = "resources.rc",
    hdrs = ["resource_ids.h"],
    data = ["logo.ico", "payload.txt"],
    defines = ["PRODUCT_VERSION=7"],
    out = "resources.res",
)
```

The input is UTF-8 (`wrc -u`). Declare every included header and embedded asset,
including generated files, in `hdrs` and `data`. Their parent directories, the
source's parent, and the bundled Wine headers form the search path. An RC source
generated by `wine_message_file` can be passed directly as `src`.
For qualified paths such as `#include "sub/resource.h"`, use package-relative
`includes = ["generated"]` when the declared header is generated at
`generated/sub/resource.h`. These explicit roots are searched in both the source
tree and generated output tree, including with path mapping enabled.
Entries use forward slashes and stay within the rule's package: absolute paths,
Windows drive/UNC paths, backslashes and `..` components are rejected. `.` or an
empty entry denotes the package root. Inputs must still be explicitly declared.

## IDLs

```starlark
load("@rules_wine//wine:wine_idl_files.bzl", "wine_idl_files")

wine_idl_files(
    name = "interfaces",
    src = "interfaces.idl",
    imports = ["base.idl", "company.tlb"],
    header = "interfaces.h",
    typelib = "interfaces.tlb",
    proxy = "interfaces_p.c",
    iid = "interfaces_i.c",
)
```

Select at least one output: `header`, `typelib`, `client`, `server`, `proxy` or
`iid`. Each is an ordinary generated file label. One invocation owns each output,
so no unselected or content-dependent output is promised. Generated C uses
interpreter stubs (`-Oif`) and includes the selected header's basename. If
`header` is omitted, upstream uses the input basename with `.h`. Imported IDLs
can require their own generated headers when compiling the resulting C; declare
those as separate generation targets. Consumers own C/C++ include paths,
compilation and linking; these rules do not return `CcInfo`.

The configured **target CPU** selects `x86_64-w64-mingw32` or
`aarch64-w64-mingw32`, regardless of the native tools' CPU. Other target CPUs
fail analysis. There is no separate architecture attribute. A Windows target
platform can be selected with `--platforms` or a consumer-owned transition when
only a dependency needs Windows generation. Message/resource rules remain
CPU-neutral. The bundled `stdole2.tlb` matches the selected target CPU.

`includes` also supports package-relative source/generated roots for IDL
preprocessor `#include` directives. Wine's IDL `import` intentionally bypasses
`-I` for names containing directory paths: use basename imports for generated
IDL files, with the declared file in `imports`. This preserves upstream WIDL
semantics; source paths are not rewritten.

## Declared data and reproducibility

The distribution's headers/IDLs, both standard typelibs, and Unix NLS data are
declared action inputs. `wrc` and `widl` use `--nostdinc` with explicit `-I` and
`-L` arguments, disabling their implicit host include and typelib searches.
Unix `wmc`/`wrc` receive an explicit `--nls-dir`. Wine retains its fallback NLS
search, but the complete bundled data supplies the supported codepages.
These compiler input definitions are not a replacement C/C++ Windows SDK.

Upstream `wrc`/`widl` expand `__DATE__` and `__TIME__` using wall-clock time, even
when command-line definitions attempt to override them. Avoid these macros in
cached builds. `wmc` embeds its command line in RC/header comments; output roots
and mapped paths can therefore change those comments. Normal fixtures are
checked for stable content when repeated with the same action paths; this does
not promise reproducibility for arbitrary source inputs.

File arguments stay typed until expansion. Optional Bazel 8/9 path mapping can
be enabled with `--experimental_output_paths=strip` and
`--modify_execution_info=WineMessageCompile|WineResourceCompile|WineIdlCompile=+supports-path-mapping`
(quote that flag in a shell). Local Linux/macOS sandboxes support this; local
Windows does not provide a mapping-capable sandbox. Paths embedded inside input
files or preprocessor definitions remain the caller's responsibility.

## Executable tools

`@rules_wine//wine:wmc`, `:wrc` and `:widl` are executable targets. The same
`register_toolchains("@wine_tools_toolchains//:all")` setup enables them. For
example, with a direct `bazel_lib` dependency in your module:

```starlark
load("@bazel_lib//lib:run_binary.bzl", "run_binary")

run_binary(
    name = "custom_resource",
    srcs = ["application.rc"],
    outs = ["application.res"],
    args = ["-u", "-o", "$(location application.res)", "$(location application.rc)"],
    tool = "@rules_wine//wine:wrc",
)
```

You can also use `bazel run @rules_wine//wine:widl -- -V`. A tiny native
forwarding launcher preserves the original executable's installation paths and
runfiles. Its template and finalizer are prebuilt; no consumer compiler, Wine
runtime or supervisor is involved. Executable selection follows the configured
target platform, which is the consuming action's executor for `run_binary`.
The launcher finalizer may run on a different executor.

These targets supply the complete distribution but add no compiler flags.
Declare imports, headers and assets in `srcs`, and provide search paths and the
WIDL target ABI in `args` when needed. `run_binary` owns its string expansion
and path-mapping behavior; the generation rules' typed-File guarantees do not
apply to these raw arguments.

`wrc -u` selects UTF-8 source encoding. Non-ASCII `-D` values are unsupported
on native Windows; keep non-ASCII resource text in declared UTF-8 source files
or headers.

## Custom distributions and low-level actions

For a genrule, request `toolchains = ["@rules_wine//wine:tools_toolchain_type"]`
and invoke `"$(WINE_WMC)"`, `"$(WINE_WRC)"` or `"$(WINE_WIDL)"` in `cmd`.
These variables contain only executable paths; commands own flags and shell
quoting. The resolved toolchain supplies the complete distribution as declared
inputs. For custom executable targets with runfiles, also list those executable
labels in `tools`: Bazel materializes their runfiles through that attribute.
The generation rules already preserve custom executable runfiles automatically.
For example:

```starlark
genrule(
    name = "custom_typelib",
    srcs = ["interfaces.idl"],
    outs = ["interfaces.tlb"],
    cmd = '"$(WINE_WIDL)" -b x86_64-w64-mingw32 -t -o "$@" "$(location interfaces.idl)"',
    toolchains = ["@rules_wine//wine:tools_toolchain_type"],
)
```

Acquire a custom native tools archive with `http_archive`, export its executable
files, and define an implementation in `BUILD.bazel`:

```starlark
load("@rules_wine//wine:tools_toolchain.bzl", "wine_tools_executable_toolchain", "wine_tools_toolchain")

distribution = dict(
    wmc = "@company_tools//:bin/wmc",
    wrc = "@company_tools//:bin/wrc",
    widl = "@company_tools//:bin/widl",
    files = "@company_tools//:files",
    include = "@company_tools//:include/wine/windows/windows.h",
    nls = "@company_tools//:share/wine/nls/locale.nls",
    x86_64_typelib = "@company_tools//:lib/wine/x86_64-windows/stdole2.tlb",
    aarch64_typelib = "@company_tools//:lib/wine/aarch64-windows/stdole2.tlb",
)
wine_tools_toolchain(name = "company_tools_impl", **distribution)
wine_tools_executable_toolchain(name = "company_executables_impl", **distribution)
toolchain(
    name = "company_tools",
    toolchain = "company_tools_impl",
    toolchain_type = "@rules_wine//wine:tools_toolchain_type",
    exec_compatible_with = ["@platforms//os:linux", "@platforms//cpu:x86_64"],
)
toolchain(
    name = "company_executables",
    toolchain = "company_executables_impl",
    toolchain_type = "@rules_wine//wine:tools_executable_toolchain_type",
    target_compatible_with = ["@platforms//os:linux", "@platforms//cpu:x86_64"],
)
```

Register with `register_toolchains("//:company_tools", "//:company_executables")`.
The first registration serves generation rules and genrules; the second serves
the executable labels. Put all executor constraints, including custom worker
constraints, in `target_compatible_with` for the second registration. This
avoids choosing tools for the launcher's own build executor. For native Windows,
use `.exe` executable paths and omit `nls`. Preserve the installation layout and
include all support files in `files`.

Custom rule authors declare the same toolchain type, resolve
`ctx.toolchains[Label("@rules_wine//wine:tools_toolchain_type")].wine_tools`, and
pass `tools.wmc`, `tools.wrc` or `tools.widl` directly to `ctx.actions.run`.
Include `tools.files` in the action's input depset. `WineToolsInfo` exposes typed
`include`, `nls` and CPU-keyed `typelibs` anchor Files: their parent directories
are the search roots. Use `Args.add_all(..., map_each = ...)` to derive directory
arguments lazily from these Files when enabling path mapping. The public
generation rules show complete native action examples.

Tool flag/output contracts follow the
[Wine 11.20 sources](https://gitlab.winehq.org/wine/wine/-/tree/wine-11.20/tools):
`wmc/wmc.c`, `wrc/wrc.c`, `widl/widl.c`, and their shared preprocessor
`wrc/wpp.c`. Archive layout and standalone invocations are qualified by
[wine-prebuilt's tools tests](https://github.com/hermeticbuild/wine-prebuilt/blob/11.20.2/tests/tools.py).
